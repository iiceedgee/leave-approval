## Q1/12 Warmup — แนะนำตัว + เล่าโปรเจคนี้ใน 1-2 นาที

**senior ถาม:** "แนะนำตัวหน่อยครับ แล้วโปรเจค leave-approval นี้ทำอะไร ใช้ stack อะไร คุณทำส่วนไหน?"

**เฉลยท่อง 30วิ:**
"สวัสดีครับ ชื่อไอซ์ครับ เป็น fullstack ประมาณ 1 ปี 9 เดือน ถนัด frontend Angular / React / HTML-CSS ส่วน backend ทำ .NET Core C# เป็นหลัก แล้วก็มี Node.js (Express) จากโปรเจคนี้ครับ โปรเจค leave-approval เป็นระบบลาพนักงานต้นแบบ เอาแนวคิดจากงานจริง (EEC) มาทำให้กระชับ — มี 3 โรลคือ emp ยื่นคำขอ, mgr/hr ช่วยกันตรวจเอกสาร แต่คนอนุมัติขั้นสุดท้ายคือ mgr คนเดียวครับ Stack คือ Angular 19 + Express + Supabase (Postgres) มีระบบสถานะ + Stepper 4 ขั้น + อัปโหลดไฟล์ + ประวัติ ส่วนที่ผมทำคือทั้งหน้าบ้าน (dashboard/ฟอร์ม/หน้า detail) และหลังบ้าน (API ลา + ระบบสถานะ) ครับ"

**ขยายความ:**
- **โปรเจคคืออะไร:** ระบบลาพนักงาน ทดลองทำ prototype จากงาน EEC ให้ flow ครบ ยื่น → ตรวจเอกสาร → อนุมัติ → ประวัติ
- **3 โรล:** `emp` ยื่น/ยกเลิก/ส่งกลับแก้ไขของตัวเอง, `hr`/`mgr` ตรวจเอกสารตอน `DC` ได้ทั้งคู่, แต่อนุมัติตอน `MA` ได้แค่ `mgr` คนเดียว — นี่คือจุดที่ต้องย้ำว่าเข้าใจ workflow ถูกต้อง
- **Stack:** `angular-ui` = Angular 19 + DxDataGrid + RxJS, `leave-api` = Express + Supabase (Postgres) + multer + JWT
- **ส่วนที่ทำจริง:** หน้าบ้าน `leave-form.component.ts` / `dashboard` / `leave-detail.component.ts` + หลังบ้าน `leave.service.js` / `file.route.js` / `status.js`
- **พูดให้ผ่าน:** อย่าพูดว่า "ให้ AI ทำ" ให้พูดว่า "เอาแนวคิดงานจริงมาทำ prototype เพื่อฝึก full flow ครับ" — บอกประสบการณ์ตรง ไม่โม้

**ถ้า senior ขยี้:**

## Q2/12 สถานะ — Flow 4 ขั้น + 3 ทางออก + stamp ประวัติ

**senior ถาม:** "เล่า flow สถานะให้ฟังหน่อย มัน stamp ยังไง? มีกี่สถานะ?"

**เฉลยท่อง 30วิ:**
"ระบบมี 4 ขั้นหลักครับ `SU` พนักงานยื่นคำขอ → `DC` รอ hr หรือ mgr ตรวจเอกสาร → `MA` รอหัวหน้า (mgr) อนุมัติคนเดียว → `AP` อนุมัติแล้วจบครับ ส่วนทางออกอื่นมี 3 ทางครับ `SB` ส่งกลับไปแก้แล้ววนกลับ `SU`, `RJ` ไม่อนุมัติ, `CX` ยกเลิกซึ่งพนักงานยกเลิกได้แค่ตอนยังเป็น `SU` ครับ ทุกครั้งที่เปลี่ยนสถานะ ระบบจะ stamp ลงประวัติไว้ดูย้อนหลังได้ครับ"

**ขยายความ:**
- **ทริคจำ:** "4 ขั้น + 3 ทางออก" คนฟังจำทันที
- **4 ขั้นหลัก:** `SU (Submitted)` → `DC (Document Check)` → `MA (Manager Approval)` → `AP (Approved)`
- **3 ทางออก:** `SB (Send Back → SU)` , `RJ (Rejected)` , `CX (Cancelled)` — `CX` ได้แค่ตอน `SU` เท่านั้น (`leave.service.js:170`)
- **stamp อย่างไร:** ทุก transition จะ `await this.db.addHistory({ leave_request_id, status_code, action_by, action_role, remark })` เช่น `leave.service.js:35` ตอน `create()` stamp `SU`, `leave.service.js:256` ตอน `transition()` stamp ทุกสถานะ
- **เก็บที่ไหน:** ตาราง `leave_status_history` มีคอลัมน์ `status_code / action_by / action_role / remark / created_at` (`leave.service.js:35` + `supabase-store.js:253 addHistory` + `store.js` InMemory `this.histories[]`)
- **อย่าพูดรหัสเก่า:** `F/S/B/C/U` คือของเก่า ตอนนี้ใช้ `SU/DC/MA/AP/SB/CX/RJ` เท่านั้น

```js
// leave.service.js:35 — stamp ตอนยื่น
await this.db.addHistory({ leave_request_id: leave.id, status_code: STATUS.SU.code, action_by: userId, action_role: 'emp', remark: 'ยื่นคำขอลา' });
// leave.service.js:256 — stamp ทุก transition
await this.db.addHistory({ leave_request_id: leaveId, status_code: targetStatus, action_by: userId, action_role: role, remark });
```

**ถ้า senior ขยี้:**
- "แล้ว stamp เก็บที่ไหน ดูย้อนหลังยังไง?" → ตอบ: "เก็บในตาราง `leave_status_history` ครับ มี `status_code / action_by / remark / เวลา` แล้วหน้า detail จะเรียก `GET /api/leave/:id/history` ผ่าน `stepper.service.js:buildHistoryTimeline` มาโชว์ timeline ครับ (`leave.service.js:278 getHistory`)"
- "ทำไมต้องมี SB แล้วกลับ SU?" → ตอบ: "เพื่อให้พนักงานแก้เอกสารแล้วส่งใหม่แบบเป็นวงจร ไม่ต้องสร้างใบใหม่ครับ (`flag_send_back='Y'` + `send_back_count++` ที่ `leave.service.js:113`)"

**ไฟล์อ้างอิง:** `leave-api/src/services/leave.service.js:35` , `leave-api/src/constants/status.js` , `leave-api/src/db/supabase-store.js:253` , `leave-api/src/store.js`

## Q3/12 Stepper — หน้า detail 4 จุด รู้ได้ไงว่าขั้นไหน done/current/pending

**senior ถาม:** "หน้า detail มี Stepper 4 ขั้น มันรู้ได้ไงว่าขั้นไหน done / current / pending? แล้วถ้าส่งกลับหรือไม่อนุมัติล่ะ?"

**เฉลยท่อง 30วิ:**
"Stepper จะดูจากสถานะปัจจุบันครับ ถ้าผ่านขั้นไหนไปแล้วจะเป็นสีเขียว (done) ขั้นที่กำลังทำอยู่จะเป็นสีน้ำเงินเข้ม (current) ส่วนขั้นที่ยังไม่ถึงจะเป็นสีเทา (pending) ครับ เช่นตอน `SU` ขั้น1 น้ำเงิน ที่เหลือเทา พอไป `DC` ขั้น1 เขียว ขั้น2 น้ำเงิน พอ `AP` ก็เขียวหมด 4 ขั้น ถ้าโดนส่งกลับจะกลับมาขั้น1 เป็น current ใหม่ ส่วนถ้าไม่อนุมัติหรือยกเลิก ขั้นสุดท้ายจะกลายเป็นสีแดงครับ"

**ขยายความ:**
- **หลักการ:** `stepper.service.js:59 getStepperSteps(currentStatus, flagSendBack, history)` จะ map `BASE_STEPS[0..2] + getFinalStep(currentStatus)` เป็น `state = done/current/pending/rejected/cancelled`
- **ปกติ:** `SU → ขั้น1 current`, `DC → ขั้น1 done ขั้น2 current`, `MA → ขั้น1-2 done ขั้น3 current`, `AP → done หมด 4 ขั้น` (`stepper.service.js:63 stepState`)
- **ส่งกลับ:** `flag_send_back='Y' → ขั้น1 current ที่เหลือ pending` (`stepper.service.js:74`)
- **ไม่อนุมัติ/ยกเลิก:** `RJ → ขั้นสุดท้าย rejected แดง`, `CX → cancelled แดง` ส่วนขั้นก่อนหน้า `done/pending` ตาม `maxReached` (`stepper.service.js:66-72`)
- **สี:** เขียว `done` / น้ำเงิน `current` / เทา `pending` / แดง `rejected/cancelled` — ต้องพูดครบ 4 สี senior จะหยุดถาม

```js
// stepper.service.js:63 — หัวใจการตัดสินใจ
if (currentStatus === STATUS.AP.code) return 'done';
if (currentStatus === STATUS.RJ.code) { if (index===3) return 'rejected'; return index<=maxReached?'done':'pending'; }
if (flagSendBack==='Y' && index===0) return 'current';
if (currentStatus===STATUS.SU.code) { if(index===0) return 'current'; return 'pending'; }
```

**ถ้า senior ขยี้:**
- "แล้ว code ดูยังไง?" → ตอบ: "ใน `getStepperSteps` จะเช็ค `current_status` กับ `flag_send_back` แล้ว map เป็น `done/current/pending` ครับ ไม่ต้องท่อง if ทั้งหมด (`stepper.service.js:63`)"
- "ถ้า history ว่างแต่เป็น RJ/CX?" → ตอบ: "มี fallback `maxReached=0` ให้ขั้นแรกเป็น done เพื่อไม่ให้ stepper ว่างเปล่า (`stepper.service.js:38`)"

**ไฟล์อ้างอิง:** `leave-api/src/services/stepper.service.js:63` , `leave-api/src/services/leave.service.js:268 getStepper` , `angular-ui/src/app/features/leave-detail/`

## Q4/12 Backend — ทำไมต้องมี State Gate 2 ชั้น

**senior ถาม:** "ถ้าไม่มี State Gate จะเกิดอะไรขึ้น? ทำไม approve ต้องเช็ค MA เท่านั้น?"

**เฉลยท่อง 30วิ:**
"ถ้าไม่มี State Gate หัวหน้าจะกดอนุมัติจาก `SU` ได้เลยทั้งที่ยังไม่ได้ตรวจเอกสารครับ ทำให้ข้ามขั้นตอน workflow พัง หน้าบ้านผมซ่อนปุ่มไว้แล้วครับ (`canApprove = isMgr && status === MA` ถึงจะโชว์) แต่ถ้าคนรู้ API ก็ยิงตรงด้วย Postman ได้เลย ผมเลยต้องมี Gate ที่หลังบ้านด้วยครับ ใน `leave.service.js` ตรง `approve` จะเช็คว่าต้องเป็น `MA` เท่านั้น ไม่งั้นตอบ 400 ว่า 'อนุมัติไม่ได้ สถานะไม่ใช่รอหัวหน้าตรวจสอบ' เป็นการกัน 2 ชั้นครับ"

**ขยายความ:**
- **ถ้าไม่มี gate:** `emp` ยื่น `SU` ปุ๊บ `mgr` ยิง `POST /api/approval/:id/approve` ได้เลยโดยไม่ผ่าน `DC` → workflow หลอก เอกสารไม่ถูกตรวจ
- **กันชั้นที่ 1 หน้าบ้าน:** `leave-detail.component.ts: canApprove / canDoPretemp` ซ่อนปุ่มถ้า `role!=='mgr' || status!=='MA'` — ผู้ใช้ทั่วไปกดไม่ได้ แต่กันได้แค่ UI
- **กันชั้นที่ 2 หลังบ้าน (สำคัญกว่า):** `leave.service.js:83` เช็คจริง

```js
// leave.service.js:83 — State Gate ของจริง
if (leave.current_status !== STATUS.MA.code) return { error: 'ไม่สามารถอนุมัติได้ สถานะปัจจุบันไม่ใช่รอหัวหน้าตรวจสอบ (MA)' };
// leave.service.js:77-86 approve() — แถมเช็ค role
if (role !== 'mgr') return { error: 'เฉพาะหัวหน้า (mgr) เท่านั้นที่อนุมัติได้' };
const res = await this.transition(leaveId, userId, role, STATUS.AP.code, remark, STATUS.MA.code);
```

- **ทุก action มี gate:** `sendBack` เช็ค `DC/MA` (`leave.service.js:96`), `reject` เช็ค `DC/MA` (`leave.service.js:148`), `cancel` เช็ค `SU` (`leave.service.js:170`)
- **Atomic ปิดท้าย:** `transition()` จะใช้ `UPDATE ... WHERE current_status='MA'` กันคนชิงกันด้วย (ดู Q12)

**ถ้า senior ขยี้:**
- "ยิง Postman จะเป็นไง?" → ตอบ: "จะโดน 400 ครับ เพราะหลังบ้านเช็คสถานะก่อนเปลี่ยนทุกครั้งครับ"
- "แล้วถ้าหน้าบ้านซ่อนปุ่มพอไหม?" → ตอบ: "ไม่พอครับ ปิดแค่หน้าบ้าน ยิงตรงได้ ต้องกันที่หลังบ้านด้วยครับ — นี่คือหลัก `never trust client` ครับ"
- "แล้ว `sendBack` ทำไม `DC` ให้ `hr/mgr` ได้ แต่ `MA` ให้แค่ `mgr`?" → ตอบ: "เพราะ `MA` คือด่านหัวหน้าแล้ว ถ้า `hr` ส่งกลับตอน `MA` จะข้ามอำนาจหัวหน้าครับ (`leave.service.js:105`)"

**ไฟล์อ้างอิง:** `leave-api/src/services/leave.service.js:83` , `leave-api/src/services/leave.service.js:234 transition` , `angular-ui/src/app/features/leave-detail/leave-detail.component.ts: canApprove`

## Q5/12 RBAC — ใครทำอะไรได้บ้าง

**senior ถาม:** "emp / mgr / hr ต่างกันยังไง? hr อนุมัติได้ไหม?"

**เฉลยท่อง 30วิ:**
"RBAC คือสิทธิ์ตามบทบาทครับ `emp` ยื่นคำขอได้คนเดียว แล้วก็ยกเลิกหรือแก้ไขแล้วส่งใหม่ได้เฉพาะของตัวเองตอนยังเป็น `SU` หรือโดนส่งกลับครับ `mgr` กับ `hr` ตรวจเอกสารตอน `DC` ได้ทั้งคู่ แต่ตอน `MA` คนอนุมัติได้คือ `mgr` คนเดียว `hr` อนุมัติไม่ได้ครับ ส่วนการมองเห็น `hr` ดูได้ทั้งหมด `mgr` ดูได้แค่แผนกตัวเอง `emp` ดูของตัวเองครับ"

**ขยายความ:**
- **จำ 1 บรรทัด:** `emp = ยื่น+แก้เมื่อโดนส่งกลับ+ยกเลิกของตัวเอง (ตอน SU)` / `mgr/hr = ตรวจ DC ได้ทั้งคู่ แต่อนุมัติ MA ได้แค่ mgr` / `hr ดูทั้งหมด, mgr ดูแผนก, emp ดูของตัวเอง`
- **Code กันอย่างไร:**
  - หน้าบ้าน: `AuthGuard` กันไม่ login (`auth.guard.ts:9`), `RoleGuard` + `canApprove` ซ่อนปุ่ม
  - หลังบ้าน: `role.middleware.js` กัน route (`roleMiddleware('mgr','hr')` สำหรับตรวจ, `roleMiddleware('mgr')` สำหรับอนุมัติ), `leave.service.js:47 getLeaves` กรอง `listLeaves` ตาม `role`

```js
// leave.service.js:47 — กรองการมองเห็น
if (role==='hr') leaves = allLeaves;
else if (role==='mgr') leaves = leaves.filter(l => owner.department===mgr.department);
else leaves = leaves.filter(l => l.user_id===userId);
// leave.service.js:80 — กันอนุมัติ
if (role!=='mgr') return { error: 'เฉพาะหัวหน้า (mgr) เท่านั้นที่อนุมัติได้' };
```

- **ไฟล์อัปโหลดก็มี RBAC:** `emp` อัปได้ตอน `SU/DC` (หรือ `flag_send_back='Y'`), `hr/mgr` อัปได้เฉพาะตอน `DC` แบบ `stage='pretemp'` (`file.route.js:109-123`)
- **ปัจจุบัน:** `hr` ยังยื่นลาในฐานะ `emp` ไม่ได้แยก — ไม่ต้องพูด senior ไม่คาดหวัง junior ต้องรู้

**ถ้า senior ขยี้:**
- "แล้ว code กันยังไง?" → ตอบ: "หน้าบ้านใช้ `RoleGuard` กับ `canApprove` ซ่อนปุ่ม หลังบ้านใช้ `role.middleware('mgr','hr')` กันอีกชั้นครับ (`role.middleware.js` + `auth.guard.ts:9`)"
- "แล้ว `hr` เข้าหน้า `emp` ได้ไหม?" → ตอบ: "ตอนนี้กันแค่ login ครับ ถ้าจะกันตาม role ต้องเพิ่ม `RoleGuard` ที่ `role.guard.ts` ครับ"
- "RBAC คืออะไร?" → ตอบสั้นๆ: "สิทธิ์ตามบทบาทครับ ใครเป็นอะไร ทำอะไรได้บ้าง แค่นั้นเลย"

**ไฟล์อ้างอิง:** `leave-api/src/middleware/role.middleware.js` , `leave-api/src/middleware/auth.middleware.js:3` , `leave-api/src/services/leave.service.js:47` , `angular-ui/src/app/guards/auth.guard.ts:9` , `leave-api/src/routes/file.route.js:52`

## Q6/12 File Upload — ทำไมต้องแนบไฟล์ตอนยื่น

- **1) AuthGuard — ยามหน้าประตูเพจ** (`auth.guard.ts:9`)

- **2) JwtInterceptor — คนเติมบัตรผ่านทุกครั้ง** (`jwt.interceptor.ts:10`)

```ts
// jwt.interceptor.ts:10
intercept(req, next) {
  const skip = ['/auth/login', '/auth/register'];
  if (skip.some(u => req.url.includes(u))) return next.handle(req); // login/register ไม่ต้องเติม
  const token = this.auth.getToken(); // จาก localStorage 'token' auth.service.ts:33

// ลงทะเบียนที่ app.module.ts:50
```

- **3) ErrorInterceptor — คนดัก error กลาง** (`error.interceptor.ts:29`) ดัก `401 → logout + toast 'session หมดอายุ' + navigate /login` (มี `handling401` กันยิงซ้ำ), `403/404/500 → toast` ตาม `getUserFriendlyMessage`, มี `silentUrls = ['/stepper','/history','/my-balance']` ไม่ toast ให้รำคาญเพราะหน้า detail จะ `catchError(of([]))` เอง
- **4) หลังบ้านเช็คซ้ำ** (`auth.middleware.js:3` `jwt.verify(token, JWT_SECRET)` แล้ว `req.user = decoded` ได้ `id/role` มาใช้) — ต่อให้หน้าบ้านข้าม Guard ไปได้ หลังบ้านก็ยัง verify อีกรอบก่อนให้เข้า `leave.route.js / approval.route.js`
- **เทียบ React:** `React ใช้ JSX + hook ส่วน Angular โปรเจคนี้ใช้ NgModule + RxJS + Guard/Interceptor ที่ Angular มีให้เลย หลักการ component เหมือนกันครับ`

## Q11/12 ปิดท้าย — ถ้าให้ทำต่อ จะทำอะไรเพิ่ม (Pagination / httpOnly / Supabase Storage)

**senior ถาม:** "ถ้ามีเวลาเพิ่ม 1 อาทิตย์ จะปรับอะไรในโปรเจคนี้?"

**เฉลยท่อง 30วิ:**
"ถ้ามีเวลาอาทิตย์นึง ผมอยากทำ 3 อย่างครับ 1) ย้ายอัปโหลดไฟล์ไปเก็บถาวรบน Supabase Storage `bucket leave-documents` ตอนนี้บน Vercel ยังเป็น `memoryStorage` ชั่วคราวครับ (`upload.middleware.js:22`) 2) ทำแบ่งหน้า (pagination) ให้หน้า dashboard ตอนนี้ `GET /leave` โหลดมาหมด ถ้ามี 1,000 ใบจะช้า ควรทำ `?page=1&limit=20` ส่งทีละ 20 ใบครับ 3) ย้าย JWT จาก `localStorage` ไปเป็น `httpOnly cookie` กัน XSS ครับ"

**ขยายความ:**
- **1) Supabase Storage — แก้ไฟล์หายบน Vercel** (`upload.middleware.js:22`)

```js
// upload.middleware.js:22
const storage = isVercel ? multer.memoryStorage() : multer.diskStorage({destination: uploads/:id})
// Local: เก็บลง uploads/:id/uuid.pdf บนดิสก์ ถาวร
// Vercel: ดิสก์ read-only (นอกจาก /tmp) เลยต้อง memoryStorage → ไฟล์อยู่ในแรม → file.service.js เอา buffer ไป supabase.storage.from('leave-documents').upload() ต่อ ถ้าไม่ต่อ bucket ไฟล์จะหายเมื่อ function จบ
```

ตอนนี้ต้องให้ `FileService` อัป `buffer` ต่อเข้า `leave-documents` bucket ถึงจะไม่หาย — บน Vercel `GET /:id/files/:fileId` จะ `createSignedUrl` แล้ว redirect (`file.route.js:224`)

- **2) Pagination — แบ่งหน้า** ตอนนี้ `leave.service.js:47 getLeaves` โหลด `listLeaves()` มาทั้งหมดแล้ว `map` — ถ้ามี 1,000 ใบจะช้า ควรทำ `GET /api/leave?page=1&limit=20` แล้ว `supabase.from('leave_requests').range(0,19).order('updated_at')` ส่งทีละ 20 ใบ — พูดแค่นี้ junior ผ่าน ไม่ต้องลง `OFFSET/LIMIT` SQL
- **3) httpOnly cookie — กัน XSS**

```js
// ปัจจุบัน
localStorage.setItem('token', jwt) // auth.service.ts:17 — JS อ่านได้ → โดน XSS ขโมยได้
// ที่ควรทำ
res.cookie('token', jwt, { httpOnly: true, secure: true, sameSite: 'strict' }) // JS อ่านไม่ได้ เบราว์เซอร์ส่งให้อัตโนมัติ
```

`httpOnly` คือคุกกี้ที่ `JS` อ่านไม่ได้ เบราว์เซอร์จะส่งให้อัตโนมัติ แฮกเกอร์ขโมยจาก `localStorage` ไม่ได้ — ตอนนี้ใช้ `localStorage` เพื่อให้ `JwtInterceptor` หยิบง่าย ถ้าขึ้นโปรดักชันควรเปลี่ยน

**ถ้า senior ขยี้:**
- "แล้ว pagination ทำไงให้เห็นภาพ?" → ตอบ: "หลังบ้านรับ `?page&limit` แล้ว `range()` ส่วนหน้าบ้าน `DxDataGrid` มี paging อยู่แล้วครับ"
- "แล้วถ้ายังใช้ localStorage จะอันตรายแค่ไหน?" → ตอบ: "ถ้าโดน XSS จะ `localStorage.getItem('token')` ได้เลยครับ แต่ `httpOnly` จะกันได้ครับ"
- "แล้วไฟล์บน Vercel หายจริงไหม?" → ตอบ: "หายครับ ถ้าไม่ต่อ Supabase Storage เพราะ `memoryStorage` อยู่แค่ในแรมตอน request เดียวครับ (`upload.middleware.js:22`)"

**ไฟล์อ้างอิง:** `leave-api/src/middleware/upload.middleware.js:22` , `leave-api/src/services/leave.service.js:47` , `angular-ui/src/app/services/auth.service.ts:17` , `leave-api/src/routes/file.route.js:224`

## Q12/12 กับดัก Production — 3 เรื่องที่ senior ชอบขยี้สุด (409 / Error+Toast / nextval)

**senior ถาม:** "ถ้า 2 คนกดอนุมัติพร้อมกันจะเป็นไง? ถ้า API พัง 500 จะโชว์อะไร? ทำไมไฟล์หายเมื่อ deploy? เลขรันซ้ำได้ไหม?"

**เฉลยท่อง 30วิ (3 ท่อน):**
"1) ผมกัน 2 คนกดพร้อมกันด้วย `UPDATE ... WHERE current_status='MA'` ครับ ถ้าโดนชิงไปแล้วจะไม่มีแถวกลับมา ผมก็ตอบ 409 ให้รีเฟรชครับ (`leave.service.js:244`) 2) หลังบ้านมี `errorHandler` กลางที่ `error.middleware.js:1` คอยแปลง error เป็น message ส่วนหน้าบ้านมี `ErrorInterceptor` ที่ `error.interceptor.ts:29` ดัก 401/500 แล้วเรียก `ToastService` โชว์กล่องลอยมุมขวา 4 วิครับ 3) บน Vercel ไฟล์ระบบเป็น read-only เลยใช้ `memoryStorage` ที่ `upload.middleware.js:22` ไฟล์อยู่ในแรมชั่วคราว ต้องต่อ `Supabase Storage bucket leave-documents` ถึงจะไม่หาย ส่วนเลขรัน `LV-YYYY-XXXX` ใช้ `nextval` ที่ `supabase-store.js:88` เป็น atomic ยิงพร้อมกันก็ไม่ซ้ำครับ"

**ขยายความ:**

### กับดักที่ 1 — SQL ล็อคแถว "ใครมาก่อนได้ไป คนมาทีหลังติด 409" (`leave.service.js:234`)

```js
// leave.service.js:234 transition() — ของจริงที่ approve/reject/sendBack เรียก
updated = await this.db.updateLeaveWhere(leaveId, {current_status:'AP'}, {current_status:'MA'});
if (!updated) return { error: 'ถูกดำเนินการไปแล้ว กรุณารีเฟรช', statusCode: 409 };
// supabase-store.js:240 — แปลงเป็น SQL จริง
// UPDATE leave_requests SET current_status='AP', updated_at=now()
// WHERE id=:id AND current_status='MA'  -- ← ล็อคด้วย WHERE
// RETURNING *; -- ถ้าไม่มีแถวกลับมา = โดนคนอื่นชิงไปแล้ว
```

- **ภาพง่ายๆ:** 2 หัวหน้าเปิดใบเดียวกันตอน `MA` พร้อมกัน คนแรกกดอนุมัติ → `MA→AP` สำเร็จ คนที่สองกดตาม → `WHERE current_status='MA'` หาไม่เจอแล้ว (ตอนนี้เป็น `AP`) → ได้ `null` → ตอบ `409` ให้รีเฟรช
- **ทำไมไม่ใช้ `SELECT FOR UPDATE`?** ใช้ **Optimistic Lock** แบบ `WHERE + RETURNING` ง่ายกว่า ไม่ต้องเปิด transaction ยาว (`leave.service.js:202 resubmit` กับ `file.route.js:157 auto SU→DC` ใช้วิธีเดียวกัน)
- **ไฟล์เกี่ยว:** `leave.service.js:77 approve`, `leave.service.js:108 sendBack`, `leave.service.js:158 reject`, `leave.service.js:234 transition`, `leave.service.js:202 resubmit`, `supabase-store.js:240 updateLeaveWhere`, `store.js:129 updateLeaveWhere`

### กับดักที่ 2 — `error.middleware.js + error.interceptor.ts + Toast` คืออะไร?

- **Toast = กล่องข้อความลอยมุมขวาบน 4 วิแล้วหาย** (`toast.service.ts:20-60`)

```ts

```

- **หลังบ้าน** (`error.middleware.js:1-14`) ด่านสุดท้าย กัน stack หลุด


- **หน้าบ้าน** (`error.interceptor.ts:29-64`)

### กับดักที่ 3 — Vercel `memoryStorage` + `request_no LV-YYYY-XXXX nextval`

- **ทำไมไฟล์หาย?** (`upload.middleware.js:22`)

```js
const storage = isVercel ? multer.memoryStorage() : multer.diskStorage({destination: uploads/:id})
// Vercel filesystem is read-only (except /tmp) → ต้อง memoryStorage
// Local: ไฟล์อยู่ disk ถาวร / Vercel: ไฟล์อยู่ buffer ในแรม → file.service.js เอา buffer ไป supabase.storage.from('leave-documents').upload() ต่อ ถ้าไม่ต่อ bucket ไฟล์จะหายเมื่อ function จบ
```

บน Vercel `GET /:id/files/:fileId` จะ `createSignedUrl(file.file_path, 60)` แล้ว redirect (`file.route.js:224`) ถ้าไม่มี supabase จะ `404`

- **เลขรันซ้ำได้ไหม?** (`supabase-store.js:82`)

```js
// supabase-store.js:82 _nextRequestNo()
const {data} = await supabase.rpc('next_request_no'); // nextval แบบ atomic ใน Postgres
// fallback เดิม MAX+1 → 2 คนอ่าน max เดียวกัน 09:00:00.001 ได้เลขเดียวกัน → 23505 duplicate
// ตอนนี้ nextval('leave_request_no_seq') เป็น atomic ต่อให้ยิงพร้อมกันก็ได้ 0001,0002 ไม่ซ้ำ ถ้าซ้ำจริงก็ retry 3 รอบ (supabase-store.js:147)
```

`LV-2026-0001` ตอนแรกใช้ `MAX+1` แล้ว `+1` ในแอป ทำให้ 2 request อ่าน `max` เดียวกันได้เลขเดียวกันแล้ว `23505 unique violation` ต้อง retry — ตอนนี้แก้ด้วย `nextval` แล้ว + มี `retry 3 รอบ` กัน `23505` (`supabase-store.js:175`)

**ถ้า senior ขยี้:**
- "แล้วถ้าไม่ใช้ WHERE จะเกิด race ยังไง?" → ตอบ: "2 คนจะ `UPDATE` ทับกัน คนหลังชนะ คนแรกหายครับ แต่พอใช้ `WHERE status='MA'` คนหลังจะได้ 0 rows → 409 ครับ"
- "แล้ว Toast อยู่ตรงไหน?" → ตอบ: "`toast.service.ts:47 add()` แล้ว `toast.component.html` โชว์มุมขวา `*ngFor` ครับ"
